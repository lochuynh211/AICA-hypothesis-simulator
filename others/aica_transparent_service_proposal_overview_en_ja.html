AICA 透明サービス提案アルゴリズム — CDC-SU ベースライン V1AICA transparent service-proposal algorithm — CDC-SU baseline V1

一言で言うと：発火（提案機会）が確定した後に、どのサービスをどの順で提案するかを決めます。各特徴量の evidence e_i（状況の強さ）× response coefficient a_i（その候補サービスがどれだけ応えるか — スライド67由来の手動係数）を、階層重みで加重合計し service_fit ∈ [-1,+1] を出します。上位3件を返します。service_fit は受諾確率でも回復効果でも安全保証でもありません。 In one line: after the trigger has established a proposal opportunity, this ranks which services to propose. Each feature multiplies evidence e_i (how strongly the context calls for something) by a response coefficient a_i (how well the candidate service answers it — a hand-authored value derived from Slide 67), weighted by the feature hierarchy and summed into service_fit ∈ [-1,+1]. Returns the top three. service_fit is not an acceptance probability, a recovery effect, or a safety certification.

1概要 ― 考え方Overview — the idea

すべての特徴量は同じ形をとります：evidence e_i（現在の世界の強さ）× response coefficient a_i（その候補がどれだけ応えるか）。evidence は世界スナップショットから一度だけ読み、係数は候補サービスIDの固有プロパティで、スライド67とサービス定義（スライド38–40）から導きます。各特徴量の r_i = e_i·a_i を階層重みで拡大し合計します。絶対的な安全は採点前のハード適格性が担い、相対的な適合は可視・編集可能な重みと係数で表します。 Every feature takes the same shape: an evidence value e_i (how strong the current world is) times a response coefficient a_i (how well this candidate answers it). Evidence is read once from the world snapshot; the coefficient is a stable property of the candidate service ID, derived from Slide 67 and the service definitions (Slides 38–40). Each feature's r_i = e_i·a_i is scaled by its hierarchical weight and summed. Absolute safety lives in hard eligibility (before scoring); relative suitability lives in visible, editable weights and coefficients.

service_fit は比較のための仮説スコアです。状況／好み／過去実績の小計は同じ寄与の説明用ビューで、追加の並べ替えキーにはならず、二重計上もしません。service_fit is a comparative hypothesis score. The Situation / Preference / History subtotals are explanatory views of the same contributions — never an extra sort key, never double-counted.

範囲は構造で保証（隠れclampなし）Bounds hold by construction (no hidden clamp)

各係数は |a_i| ≤ 1、evidence は [-1,+1]、よって r_i ∈ [-1,+1]。重みは非負で総和1なので Σ k_i ∈ [-1,+1]。最終の clamp は浮動小数の誤差対策のみで、不正入力による範囲外を隠しません。 Each coefficient satisfies |a_i| ≤ 1, evidence is in [-1,+1], so r_i ∈ [-1,+1]. Weights are non-negative and sum to one, so Σ k_i ∈ [-1,+1]. The final clamp guards only floating-point drift — it must never conceal an out-of-range value from invalid input.

「実効重み」とは（3行で）What “effective weight” means (three lines)

base_weight_i   = category_weight × subgroup_weight × leaf_weight
raw_weight_i(p) = base_weight_i × purpose_multiplier[p][subgroup]
w_i(p)       = raw_weight_i(p) / Σ_j raw_weight_j(p)

目的は重みを変えますが、候補の応答プロファイルは段階に依らず不変（§3）。ライフサイクル段階は別の重みセットを選ばず、候補ファミリーを選ぶだけです。数値規則：IEEE-754 binary64、固定17特徴量順、NaN/±∞は拒否、フル精度で順位付け・表示時のみ丸め、−0は+0に、厳密同点は candidate_id 昇順、許容差 1e-12。 Purpose changes weights, but a candidate's response profile is stage-independent (§3). Stage selects the family, not another weight set. Numeric rules: IEEE-754 binary64; fixed 17-feature order; reject NaN/±inf; full-precision ranking, round only for display; −0→+0; exact ties by candidate_id ascending; tolerance 1e-12.

3レスポンス係数 — どう決めるかResponse coefficients — how they are set

レスポンス係数は「この証拠があるとき、この候補サービスは適切に応えるか・中立か・矛盾するか」に答えます。ドライバーのデータから学習したものではありません。既定値は粗い5段階のアンカー集合から採りますが、パラメータ記録も下の表もコード（クラス名）ではなく数値そのものを保持します。 The coefficient answers: “when this evidence is present, does this candidate service respond appropriately, remain neutral, or conflict?” It is not learned from driver data. Defaults come from a coarse five-value anchor set — but the parameter record and every table below store the number directly, not a class code.

係数を決める3つの規則The three derivation rules

1 · 1候補IDにつき1プロファイルOne profile per candidate ID

サービスの応答は候補IDの固有プロパティで、目的・段階で変わりません。目的は重みだけを変え（マルチプライヤ、§6）、段階は適格ファミリーを選ぶだけ。だから休憩前①と走行中②–④の走行サービスは1つのマトリクスを共有します。A service's response is a stable property of the ID; it does not change with purpose or stage. Purpose changes only weights (§6); stage only selects the family. So before-rest ① and active-driving ②–④ share one driving matrix.

2 · 方向はスライド67、大きさは出典の強さDirection from Slide 67, magnitude from source strength

スライド67が明示的に優先と名指すサービス→ +1.0。あり得るが名指しされないサービス→ 弱い +0.5。無関係→ 0.0。負は正規化文脈の安全推論（山道）のみ。A service Slide 67 names as preferred → +1.0; plausibly capable but unnamed → mild +0.5; irrelevant → 0.0. Negatives only from normalized-context safety reasoning (mountain).

3 · 沈黙は中立、負ではないSilence is neutral, not negative

スライド67が優先サービスを挙げない場合（例：目的①のドライバー／環境列は「ー」）、ラベル付きの仮説がない限り 0.0（neutral_source_silent）。Where Slide 67 lists no preferred service (e.g. the ① driver/environment column is ー), the coefficient is 0.0 (neutral_source_silent) unless a labeled hypothesis justifies otherwise.

アルゴリズムの心臓部：各特徴量が読む証拠と、各候補サービスの応答。ライフサイクル・ファミリーごとに3つのマトリクスがあります。各セルは数値係数 a_i(c)。 The heart of the algorithm: what evidence each feature reads, and how each candidate service answers. Three matrices, one per lifecycle family. Every cell is the numeric coefficient a_i(c).

1つの規則：evidence × responseOne rule: evidence × response

r_i(c) = clamp( e_i(c) · a_i(c), −1, +1 )     |  道路種別のみroad type only: e=1 → r = a_road(c)

証拠には2つの形があります。片方向 e ∈ [0,1]（0＝証拠なし、＝負ではない：眠気・疲労・単調・渋滞・夜間・ルート・目的地・子供・グループ・推し登録・新規性）。両方向 e ∈ [-1,+1]（0＝中立：推しモード・全体/場面利用度・受諾率・回復率）。 Evidence has two shapes. The finer “energize a drowsy driver, soothe a fatigued one” distinction is the content selector's job — expressed there as the arousal/valence song response (drowsiness +0.80·A_s, fatigue −0.50·A_s), not as a service choice.

対比テスト（一部）Contrast tests (selected)

カタログ・目的・設定・シードを固定し、1変数だけ変えて並べ替えを検証：低↔高 眠気/疲労/単調、通常↔渋滞、高速↔山道、昼↔夜；子供在/不在；推しモード off/on；サービス新規性；全体利用度；回復率；route_music↔inattentive（ルート/目的地の重み移動で音楽↔鼻歌が入替）；山道↔高速（相互作用重サービス＝クイズ/ランキングが山道で下がる）。全適格候補は常に順位付けされ（低スコアで抑制されない）、ハード除外は復活しません。 Freeze catalog/purpose/config/seed, change one field, assert the reorder: low↔high drowsiness/fatigue/monotony; normal↔congested; highway↔mountain; day↔night; child absent↔present; oshi mode off↔on; service recency; overall usage; recovery; route_music vs inattentive (route/destination weight shift reorders music vs humming); mountain vs highway (interaction-heavy quiz/ranking drop on mountain). Every eligible candidate is always ranked (never suppressed by a low score); a hard exclusion is never reinstated.

9設計判断と保留Design choices & deferred

radio の解決（スライド39 vs 70）radio_style resolution

スライド70はコンテンツ層なのでサービス係数を左右しません。スライド39が radio を推しサービスと定義するため、推しに +1.0（他特徴は 0.0）。可用性はさらに「新しい推し情報あり」フラグで適格性ゲート。Slide 70 is content-level and doesn't drive service coefficients. Slide 39 defines radio as the oshi service, so oshi = +1.0 (else 0.0). Availability is additionally gated by a “new oshi info” eligibility flag.

一様な活性化係数Uniform activation coefficients

スライド67が眠気+疲労を1行で扱い4サービスを序列なしで名指すため、サービス層では一様 +1.0。細かな区別はコンテンツ選択の arousal/valence が担います。Slide 67 puts drowsiness+fatigue in one row and names four services without ranking, so a uniform +1.0 is source-faithful; the finer distinction is the content selector's arousal/valence job.

結果・エラー区分Result & error categories

ranked_candidates · no_proposal · invalid_request · invalid_catalog · invalid_configuration。型付きエラーは証拠を持ち、未宣言のフォールバック・サービスや捏造順位を出しません。 Typed errors carry evidence and never produce an undeclared fallback service or a fabricated ranking.

保留（別パッケージ）Deferred

確率的な不確実性ランキング（重み・係数の設定範囲をサンプルし、期待fit・fit区間・首位確率を報告 — 順位の安定性であって受諾/回復確率ではない）。また候補ごとの推しメンバー/グループ・グラフ、信頼度加重の疎履歴。A probabilistic uncertainty-ranking package (samples ranges around weights/coefficients to report expected fit, a fit interval, and probability of ranking first — rank stability, not acceptance/recovery probability). Also per-service oshi member/group graphs and confidence-weighted sparse history.
