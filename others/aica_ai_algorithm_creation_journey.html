AICA Hybrid Trigger · Collaboration Case Study

How we created the AICA Hybrid Trigger

This document records the inputs we gave AI, the first algorithm proposal, the specification and implementation work, the feedback we received, and the changes made afterward.

The operating model

One cycle, eight clear stages

Each stage produces something reviewable. This keeps AI fast without making the process opaque.

1. Collect

Gather the complete business and use-case context into one input pack.

2. Understand

Extract goals, actors, signals, constraints, and gaps into a shared model.

3. Propose

Generate a first algorithm concept and compare alternative approaches.

4. Specify

Turn the selected idea into an explicit algorithm and decision contract.

5. Implement

Translate every approved rule and state into an executable package.

6. Test

Exercise normal, boundary, recovery, and failure cases to produce evidence.

7. Review

Turn domain, product, technical, and user feedback into clear findings.

8. Improve

Revise assumptions, specification, code, and explanation into the next version.

Stage 02 · Understand

Build a shared model before a formula

The first AI output should be an analysis of the problem—not code. People correct the model while changes are still inexpensive.

Human team provides
  • Source authority and business intent
  • Meaning of ambiguous terms
  • Acceptable and unacceptable outcomes
  • Known gaps and real-world exceptions
⇄
AI helps synthesize
  • Actors, events, inputs, outputs, and states
  • Contradictions across documents
  • Assumptions that need confirmation
  • A cross-use-case decision table

Stage 03 · Propose

The first AICA algorithm idea

Use a transparent hybrid: understandable rules establish boundaries, weighted signals combine context, and stateful controls keep decisions stable over time.

The first proposal combined explicit rules with weighted signal scores.

signals → normalized features → weighted scores → states → fire control → proposal
RulesHard boundaries and explicit conditions
ScoresMultiple weak signals become one readable strength
MemorySmoothing and persistence reduce noisy switching
ControlsCooldown, suppression, override, and priority

AICA example: the implemented hybrid includes feature scoring, smoothed scores, persistence counters, decision states, proposal controls, and evidence fields. Exact coefficients remain configurable rather than being treated as universal truth.

Why this idea

Requirements became design choices

The proposal is explainable because every major component answers a specific need found in the inputs.

Stakeholders must understand why a proposal appeared
→
Transparent features, thresholds, and reason inputs
No single signal tells the full story
→
Weighted multi-signal scores
Sensor and context values can fluctuate
→
Smoothing, state bands, and persistence
Repeated prompts can annoy or distract the user
→
Cooldown, history, and suppression
Urgent situations should not wait for a normal score
→
Explicit override path and priority handling
The team will learn after simulation
→
Named, tunable parameters and per-tick evidence
Stage 04 · Specify

Turn the idea into a contract

A useful algorithm specification is precise enough that implementation and review teams can reach the same interpretation.

Inputs and unitsAvailable signals, context, history, defaults
Feature transformationsNormalization, bands, accumulation, missing data
Scores and weightsFormula, range, meaning, configurable coefficients
States and transitionsEntry, persistence, recovery, and reset behavior
Decision and priority rulesCandidate selection, suppression, override
Outputs and explanationProposal, category, score, reasons, evidence
Edge cases and failure policyMissing inputs, invalid configuration, no action
Examples and acceptance testsConcrete scenarios with expected outcomes
Optional technical view: what makes the AICA hybrid stateful?
It carries smoothed features and scores, persistence counters, current rest and monotony states, time accumulators, baselines, and the previous simulation time between evaluation ticks. This lets the next decision depend on recent behavior, not only the current instant.
Stages 05–06 · Implement & test

Make every sentence observable

The simulator became the shared review surface: the team could run scenarios, inspect decisions, see reasons, and compare behavior with the specification.

1. Trace

Map each specification section to executable logic.

2. Configure

Keep thresholds and weights visible and tunable.

3. Simulate

Replay use-case situations as timed signals.

4. Inspect

Record features, scores, states, reasons, and outputs.

5. Compare

Check observed behavior against expected behavior.

Normal cases

Does each use case produce the intended proposal at a sensible time?

Boundary cases

What happens just below, at, and just above every threshold?

Temporal cases

Does persistence, cooldown, recovery, and reset behave over time?

Conflicting cases

Which candidate wins when several needs are active together?

Missing-data cases

Does unavailable context fail safely and remain visible?

Explanation cases

Can a reviewer understand why it fired—or why it did not?

Stages 07–08 · Review & improve

How feedback changed the algorithm

Reviewers compared expected behavior with simulator results. Findings were recorded with the situation, expected result, actual result, and required change.

Domain reviewDoes the behavior make sense in the real activity?
Use-case reviewDoes it fulfill all four scenarios and their priorities?
Product reviewIs the timing and message useful to the person?
Evidence loop

Run → Observe → Explain → Decide

A change is accepted only when its reason and effect are visible.

Data reviewAre features, weights, and thresholds defensible?
Engineering reviewDoes code match the specification and fail clearly?
Run feedbackWhat did reviewers accept, reject, or find confusing?

Repository-backed examples include: recovery re-trigger correction, compact tiered-signal redesign, time-on-task enhancement, manifest-based defaults, clearer formulation, and multiple UI/documentation refinements. These are examples of the cycle—not claims of real-world safety validation.

Reusable for the next project

A practical team playbook

Replace the AICA-specific content, keep the gates. The method scales because each stage has a defined input, output, and accountable reviewer.

01 · PROVIDE INPUTS

Load the real project material

Provide the project overview, all four use cases, signal definitions, constraints, and success criteria. Ask AI to list contradictions and missing information first.

02 · COMPARE IDEAS

Evaluate more than one approach

Compare candidate algorithms by transparency, required data, tunability, stability over time, and failure risk. Map each component to a requirement.

03 · WRITE THE SPEC

Define exact behavior

Document inputs, units, transformations, scores, states, transitions, decisions, outputs, parameters, edge cases, explanation fields, and acceptance examples.

04 · IMPLEMENT

Keep the code traceable

Implement the approved specification, link tests to decision rules, and expose intermediate features, scores, states, and reasons in the simulator.

05 · REVIEW RUNS

Compare expected and actual results

Check boundary failures, repeated proposals, recovery logic, unexplained decisions, and behavior that does not match the four use cases.

06 · UPDATE

Make evidence-based changes

Group feedback by root cause, change the specification first, update affected tests and code, and record the before-and-after behavior.

Human review gates

  • Problem model is correct
  • Algorithm idea fits the business need
  • Specification is unambiguous
  • Observed behavior matches intent
  • Feedback changes are approved

Definition of done

  • All input sources and four use cases covered
  • Assumptions and unknowns visible
  • Rules, parameters, states, and failures specified
  • Implementation traceable to the spec
  • Tests include time, boundaries, and recovery
  • Decisions are explainable to reviewers
Project conclusion

What AI did and what the team did

AI analyzed the documents, proposed and documented the algorithm, supported implementation, and helped process feedback. The team supplied the source material, corrected assumptions, reviewed simulator behavior, and approved each change.
