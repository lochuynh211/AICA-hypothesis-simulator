AICA 合成 Spotify互換 楽曲データ生成 — mdg パイプラインAICA synthetic Spotify-compatible music data generation — the mdg pipeline

一言で言うと：曲選びアルゴリズム（P6）をシミュレータで試すための曲カタログを作る仕組みです。曲名・アーティスト名・音の特徴・ISRC は本物のデータ（Soundcharts）をそのまま使います。一方、ID と URL は必ず架空のもの（synthetic- で始まるID、.invalid のURL）に置き換えます。AI（LLM）にできるのは「実在する曲の名前を挙げる」ことだけで、数値は1つも書けません。同じ材料と同じシード値からは、いつでも1バイトも違わない同じカタログが作れます。 In one line: this builds the song catalog the Proposal Simulator's content selector (P6) scores. Song/artist names, audio features, and ISRCs are real data (Soundcharts) copied verbatim; every ID and URL is always synthetic (synthetic- prefix, .invalid host). The LLM may only name real candidate songs — it can never write a number. The same cache + seed reproduces the catalog byte-for-byte.

1概要 ― 考え方Overview — the idea

P6 アルゴリズムを試すには、実際に採点できる曲のデータが必要です。ただ、AI に曲を丸ごと作らせると、本当かどうか確かめられず、同じ結果を再現することもできません。かといって Spotify の本物のデータを取り込むと、ライセンスの問題が出ます。そこで採ったのが「本物のデータを土台にした合成（grounded-synthetic）」という方式です。何が本物で、何が架空かを、はっきり線引きします。 Reviewing the P6 algorithm needs concrete songs. Letting an LLM invent songs wholesale is untrustworthy and unreproducible; ingesting real Spotify payloads raises licensing problems. The answer is a grounded-synthetic strategy: a hard line between what is real and what is synthesized.

なぜこの分け方かWhy this split

この分け方で、3つの利点が同時に手に入ります。（1）ライセンスの安全 — Spotify の本物のデータは保存も配信もしません。ID や URL は架空なので、本物の Spotify につながることはあり得ません（データ検査でも .invalid と synthetic- を必ず確かめます）。（2）再現できること — カタログを組み立てる工程では、ネットも AI も使いません。同じ材料と同じシード値なら、結果は毎回まったく同じです。（3）幅広さ — 本物の音の特徴を使って、曲の空間（激しさ・テンポ・タイプなど）をまんべんなくカバーします。だから P6 の2つの軸（arousal＝元気さ／valence＝明るさ）を本物のデータで確かめられます。 It buys three things at once. (1) Licensing safety — no live Spotify data is stored or served, and IDs/URLs can never resolve to a real endpoint (the schema enforces .invalid/synthetic-). (2) Reproducibility — the transform that assembles the catalog does no network or LLM I/O; same cache + seed → byte-identical output. (3) Coverage — real audio features deliberately span the feature space (energy/tempo/profile…), so P6's two trait axes (arousal/valence) are exercised with real data.

ズルを防ぐ遮断壁（FR-019）The honesty firewall (FR-019)

曲がカタログに入る理由はただ1つ、「その曲の本物の音の特徴が、埋めたいマス（セル）に当てはまるから」です。「アルゴリズムに都合のいい結果を出す曲だから」という理由で入ることは絶対にありません。スコア・ラベル・順位の情報は、生成のどの入力にも入りません（最後の凍結時にも、禁止キーが紛れていないか全体を調べ直します）。AI は数値も ISRC も書けない仕組みになっています（§4）。 A song is admitted for exactly one reason: its real audio fills a needed coverage cell — never because it would produce a desired recommendation. No score, label, or rank ever enters generation input (freeze re-scans recursively for forbidden keys, §6), and the LLM is structurally barred from writing numbers or ISRCs (§4).

2パイプライン全体像（S0→S9）The pipeline (S0→S9)

生成は S0〜S9 の番号つき工程を順に進めます。動かすのは1つのコマンド python -m mdg <工程名>（mdg/cli.py）です。工程には2種類あります：結果が毎回同じになる純粋な Python の工程と、対話型の AI にファイルを渡して返してもらう工程です。AI を API で自動呼び出しする仕組みはどこにもありません（FR-028）。AI の工程は「入力の JSON を書き出す → 端末上のエージェントが指示書どおりに出力の JSON を書く → それを検査して読み込む」の3ステップです。 The pipeline is a sequence of numbered stages driven by one CLI, python -m mdg <stage> (mdg/cli.py). Some stages are pure deterministic Python; others are file handoffs to an interactive LLM. There is no LLM API key or programmatic LLM call anywhere (FR-028) — an LLM stage is three moves: write an input JSON → the terminal agent follows a prompt and writes an output JSON → validate and read it back.

build_coverage_plan(tier, ledger)（mdg/coverage/plan.py）は、ファイルもネットも触らない純粋な関数です。「カタログにどんな曲をそろえるべきか」を、36個のマス（セル）として決めます。 build_coverage_plan(tier, ledger) (mdg/coverage/plan.py) is a pure function, no I/O. It defines the space the catalog must span as “cells.”

曲のタイプは4種類：balanced_vocal（ふつうのボーカル曲）／danceable_vocal（踊れるボーカル曲）／speech_forward（語り中心）／instrumental_leaning（楽器中心）。判定ルールは §5。バンドの間にわざと隙間を空けてあるのは、境界すれすれの曲が「どちらのマスにも入りうる」という曖昧さをなくすためです。 The four profile families: balanced_vocal / danceable_vocal / speech_forward / instrumental_leaning (decision rules in §5). The deliberate gaps between bands avoid boundary songs that could plausibly belong to either cell.

計画は「台帳（これまでの記録、§7）」を見て作られます。すでに埋まったマスは残り（remaining）から外され、まだ埋まっていないマスが次の周回の優先課題（enrichment_priority）になります。生成は一発勝負ではなく、「足りないマスを埋める周回」の繰り返しです（実績では29周、§9）。1つの条件だけが違う12組の比較ペア（§8）も、この計画で決まります。 The plan is ledger-relative: already-accepted cells are subtracted into remaining and echoed as enrichment_priority for the next loop. Generation is not one-shot — it is repeated fill loops against unmet cells (29 loops in practice, §9). The plan also defines the 12 one-variable contrast pairs requirement (§8).

4曲名出しとデータ集め（S1b–S2c）Naming & harvest (S1b–S2c)

S1b — AI は「曲名」しか出せないS1b — the LLM can only produce names

mdg name --write-input が「残っているマス・言語の目標・すでに名前が出た曲の除外リスト」を handoff/s1b_input.json に書き出します。エージェントは指示書（mdg/prompts/s1b_naming.md）に従い、マスごとに「実在していて、Web で確認できる曲」を提案します： mdg name --write-input writes remaining cells + language targets + an already-named exclusion list to handoff/s1b_input.json; the agent follows mdg/prompts/s1b_naming.md and proposes real, web-verifiable songs per cell:

CandidateName = { title, artist, release_year, expected_language, target_cell_id, why_fits_cell, web_evidence[] }
仕組みで守る遮断壁（FR-005）Structural firewall (FR-005)

CandidateName という入力の型は、isrc や12個の音の特徴のキー（energy, tempo など）が1つでも入っていたら、その場で受け付けを拒否します（mdg/models.py）。つまり AI は「この曲の energy はだいたい 0.8」と書くことすらできません。数値はすべて、あとの工程で本物のデータベースから取ります。検査に落ちると HandoffValidationError になり、エージェントは最初からやり直しです。 The CandidateName model rejects on sight any input carrying isrc or any of the 12 audio-feature keys (energy, tempo, …) (mdg/models.py). The LLM is not even allowed to write “this song is about energy 0.8” — every number comes later from the real source. A validation failure raises HandoffValidationError and the agent re-runs the prompt.

S2b — ISRC を探すS2b — ISRC resolution

ISRCResolver.resolve(曲名, アーティスト, 年)（mdg/sources/resolver.py）が MusicBrainz と Deezer に問い合わせ、候補になる ISRC（曲の国際的な識別番号）を、重複なしで優先順に並べて返します。並べ方のルール： ISRCResolver.resolve(title, artist, year) (mdg/sources/resolver.py) queries MusicBrainz and Deezer and returns an ordered, deduped candidate-ISRC list, ranked by:

rank(isrc) = ( variant_penalty, year_match, first_release_date, isrc )
# variant_penalty: karaoke/live/remix 版は後回し · year_match: 年が ±1 以内の候補を優先 · 発売が早い盤を優先versions last · year_match: |year − release_year| ≤ 1 preferred · original-release first

どちらからも ISRC が見つからなければ、song_not_found_in_sources という「ミス」として台帳に記録され、以後二度と試されません。 If neither source yields an ISRC, the candidate is ledgered as a song_not_found_in_sources miss and never retried.

S2c の前チェック — プローブ関門S2c pre-flight — the probe gate

probe: 選んでおいた約15曲を試しに取得し、12個の特徴が全部そろって返る割合がfetch ~15 hand-picked ISRCs; fraction returning all 12 features non-null ≥ 0.60 , 下回ったらelse isrc_probe_gate_failed

本格的に集め始める前に、「この年代・地域はどこまでデータがそろうか」の上限を確かめます。たとえば1960年代の日本の曲は、Soundcharts に音の特徴がそろっていないことが多いのです。 This fixes “the achievable era/region ceiling” before quota is spent — e.g. 1960s Japanese songs often lack complete audio blocks in Soundcharts.

5マス分けと選抜（S3）Binning & selection (S3)

ここが遮断壁のいちばん大事な部分です。bin_song（mdg/binner.py）は、曲がどのマスに入るかを本物の Soundcharts の音の特徴だけで決めます。AI が出した「このマスを狙った」という情報（target_cell_id）は、見ることすらしません。AI の狙いが外れていても、曲は「実際に当てはまるマス」に入るだけです。 This is the firewall's core. bin_song (mdg/binner.py) computes coverage coordinates from the real Soundcharts audio only — the LLM's target_cell_id guess is never even consulted. If the LLM's aim was off, the song simply lands in the cell it really belongs to.

# バンドの境界値（バンド間の隙間のちょうど真ん中）band boundaries (midpoints of the inter-band gaps)
energy: low ≤ 0.375 < medium ≤ 0.675 < high     tempo: low ≤ 95.5 < medium ≤ 130.5 < high

# 曲のタイプ — 上から順に、最初に当てはまったものprofile family — first matching rule in priority order
instrumental_leaning ⇐ instrumentalness ≥ 0.65
speech_forward       ⇐ speechiness ≥ 0.33 (修正済み、下記amended, below)
danceable_vocal      ⇐ danceability ≥ 0.65 ∧ instrumentalness ≤ 0.15
balanced_vocal       ⇐ 上のどれにも当てはまらない曲everything else

cell_id = 例e.g. E-hi_T-hi_P-bv
本物のデータに合わせて仕様を直した例Where real data amended the spec

もともとの仕様は speechiness ≥ 0.40 でした。ところが本物のデータでは、ラップでも 0.38 くらいが上限で、speech_forward のマスがそもそも埋められないことが分かりました（cell_unfillable_from_source）。そこで、Spotify 自身が公式に説明している「音楽＋語り」の境界 0.33 に直しました（mdg/binner.py、仕様 §10.2 の修正メモ）。都合よく数値をいじったのではなく、現実に合わない境界の定義を直した、ということです。 The original spec said speechiness ≥ 0.40, but against real Soundcharts data rap tops out around ~0.38, making speech_forward cells unfillable in principle (cell_unfillable_from_source). The threshold was amended to Spotify's own documented “music + speech” boundary of 0.33 (mdg/binner.py, spec §10.2 amendment note) — not number-tuning, but correcting the boundary's definition to match reality.

同時に補助的な座標も計算します：valence_band（明るさ、0.34／0.67 で3段階）、acousticness_band（0.50 以上ならアコースティック）、humming_ease_band／full_karaoke_ease_band（踊りやすさ・楽器度・語り度・長さのほどよさから作る「歌いやすさ」のめやす、しきい値 0.50）、era_bucket（年代）。これらは選抜の帳簿づけに使うだけで、曲データには保存されず、選抜が終わったら捨てられます。 Secondary coordinates are computed alongside: valence_band (0.34/0.67), acousticness_band (≥0.50 → acoustic), humming_ease_band/full_karaoke_ease_band (composite proxies over danceability, instrumentalness, speechiness, duration-moderateness; threshold 0.50), era_bucket. These coordinates are coverage bookkeeping only — never stored on the song, discarded after selection.

選抜は「マス埋め」方式 — スコアでは選ばないSelection is pigeonhole — never by score

select_catalog（mdg/selector.py）は、候補を「実際に測って決めたマスのID」でまとめ、重複している曲（台帳や同じ回の中で既出）だけを外します。1つのマスに何曲入ってもかまいません（周回を重ねて増やしていきます）。スコアが低いから落ちる、という曲は1曲もありません。落ちる理由は「重複」か「本物のデータが足りない」の2つだけです。 select_catalog (mdg/selector.py) groups candidates by their real binned cell ID and skips only duplicate identities (ledger or in-batch). A cell may hold several songs (loop enrichment). No song is ever rejected by score — the only rejection reasons are duplication and missing real data.

6変換・修復・凍結（S4–S6）Map, repair & freeze (S4–S6)

S4 — 変換（架空IDをつける）S4 — mapping (synthetic identity)

CatalogMapper.map_song（mdg/mapper.py）が、Soundcharts から取った生データを、決まった形（凍結スキーマ）の Song に変換します： CatalogMapper.map_song (mdg/mapper.py) converts a raw Soundcharts payload into a frozen-schema Song:

  • 架空の ID を連番でつけます：synthetic-track-0001／synthetic-album-0001／synthetic-artist-0001（アーティストは本名で重複をまとめる）。番号は ISRC を並べた順につけるので、作り直しても同じ ID になります。Sequential synthetic IDs — synthetic-track-0001 / synthetic-album-0001 / synthetic-artist-0001 (artists deduped by real name). Allocation follows the ISRC-sorted order, so IDs are stable across reruns.
  • 本物のデータはそのまま写します：曲名、音の特徴の数値、曲の長さ（秒→ミリ秒）、ISRC（external_ids.isrc へ）。Real data copied verbatim: name, audio features, real duration (s→ms), ISRC into external_ids.isrc.
  • Soundcharts にない項目のうち popularity と track_number は、sha256("シード:ISRC") から作った曲ごとの乱数で決めます（種が固定なので毎回同じ値）。available_markets は乱数ではなく、言語からの固定ルックアップです（ja→JP／en→US・GB／その他→JP・US）。Of the fields Soundcharts lacks, popularity and track_number are synthesized deterministically from a per-song PRNG seeded with sha256(f"{seed}:{isrc}"). available_markets is not random — it is a fixed lookup from language (ja→JP / en→US·GB / else→JP·US).
  • URL はすべて https://api.synthetic.invalid/...／https://open.synthetic.invalid/... の形で、実在しないアドレスです。Every URL points at https://api.synthetic.invalid/... / https://open.synthetic.invalid/....

S5 — 検査と「2回まで」の修復S5 — validation and the 2-strike repair

検査には、アプリ本体と同じ Song の型定義（aica_api.models.proposal.song_schema）をそのまま使います。mdg の中で型を作り直すことはしません。問題が見つかると4種類（identity／url／schema／flag）に分類され、決まった手順の修復を試みます： Validation runs through the app's own frozen Song model (aica_api.models.proposal.song_schema) — never redefined inside mdg. Violations are classified into four categories (identity / url / schema / flag) and deterministic repairs are attempted:

repair budget = 2 # 修復は2回まで。3回目はa third violation raises catalog_generation_failed で停止
identity → 正しい方（Track 側）の ID/URI/長さを、音の特徴側へ写し直すcopy canonical Track ID/URI/duration onto the audio-features object
url      → 正しい架空 ID から .invalid の URL を作り直すrebuild the .invalid URL from the canonical synthetic ID
schema   → 丸め誤差（clamp only within serialization noise 1e-9 以内）だけ直す — それより大きいズレは本物の壊れなので停止— anything further is real corruption and halts
flag     → 修復なし（必ず停止）no repairer (always escalates)

行った修復は、すべて {rule, field} の形で記録に残ります。どうしても直せないデータは、でっち上げて埋めるのではなく捨てて、捨てたことを記録します。 Every applied repair is logged as {rule, field}. A record that cannot be mapped or repaired is dropped, never fabricated — and the drop is logged.

S6 — 凍結S6 — freeze

1. assert_label_free(catalog) # カタログ全体をくまなく調べ、禁止キーがないか確認：recursive scan for forbidden keys: recommended, best_for_world, target_rank, item_fit, score, label, rank, why_fits_cell, web_evidence, …
2. dataset_hash = sha256( json.dumps(catalog, sort_keys=True, separators=(",",":")) )
3. manifest = { dataset_id, dataset_kind: "soundcharts_grounded_spotify_compatible", tier, versions, random_seed, generated_at }

凍結は最後の関門です（FR-019）。AI の工程で使った補助情報（why_fits_cell など）やスコアらしきキーがカタログに紛れ込んでいたら、ここで catalog_generation_failed になります。generated_at（作成日時）は外から渡します（再現テスト用の既定値は 1970-01-01T00:00:00Z）。つまり、この工程は現在時刻すら読みません。 Freeze is the last-mile firewall (FR-019): if any LLM-stage helper field (why_fits_cell, …) or score-like key leaked into the catalog, it fails right here with catalog_generation_failed. generated_at is supplied externally (defaulting to the fixed sentinel 1970-01-01T00:00:00Z for reproducibility) — the deterministic core never reads the wall clock.

7再現性と台帳Determinism & the ledger

この仕組みは、「結果が毎回変わりうるデータ集め（Soundcharts などへのネット接続）」と「毎回同じ結果になる変換」を、はっきり分けています。「同じものが必ずできる」という約束は、変換の側にあります： The system draws a hard line between the non-reproducible live harvest (network calls to Soundcharts / MusicBrainz / Deezer) and the deterministic transform. The reproducibility contract lives in the transform:

シード値が決めることSeed scope

random_seed が固定するのは3つ：架空 ID をつける順番、同点だった曲の並べ方、比較用曲（negative sample data）の配置。データ集め自体は、シードでは固定できません。random_seed pins: synthetic-ID allocation order, selection tie-breaks among equally-eligible songs, negative-sample-data placement. It does not (and cannot) pin the harvest.

曲ごとの乱数Per-song PRNG

sha256("シード:ISRC") を64ビットに縮めて random.Random の種にします。Python 標準の hash() は起動のたびに値が変わるので使いません。この方法なら、別のマシンでも同じ値になります。sha256(f"{seed}:{isrc}") truncated to 64 bits seeds random.Random. Python's built-in hash() was rejected because it is salted per process — this is stable across machines.

順番をそろえて読むSorted iteration

キャッシュはファイル名（＝ISRC）の順に読み、ID も同じ順でつけます。データを集めた時刻の順番には影響されません。Cache files are read in filename (ISRC) sorted order; ID allocation follows the same order — independent of harvest wall-clock order.

持ち越しの台帳Carry-over ledger

台帳は、曲の同一性（ISRC・UUID・整えた曲名）をキーにした「追記だけ」の記録です。おかげで周回は「積み増し」になり、同じことを二度しません：一度出た名前は再提案されず、一度失敗した曲は再挑戦されません。キーは曲の同一性だけで、スコアは絶対に入れません（FR-023/024）。だから「途中から再開できる」ことが、選抜のゆがみになりません。An append-only JSON keyed by identity tokens (ISRC / UUID / normalized name). It makes loops additive and idempotent: known names/ISRCs are never re-proposed or re-fetched, known misses never retried. Keys are identity-only — never a score (FR-023/024) — so resumability adds no selection pressure.

読み直すのは凍結カタログだけ（SC-001）Freeze is the replay boundary (SC-001)

シミュレータの透明ランが読み直すのは、コミット済みの凍結カタログです。データ集めをやり直すことはありません。「透明ランの最中に、ネット接続も AI 呼び出しも一切起きない」ことが約束です。同じキャッシュ＋同じシードで mdg transform を2回動かすと、1バイトも違わない結果になることをテストで確認しています。 A transparent simulation run replays against the committed frozen dataset — never a re-run of the harvest. “No live network or LLM call occurs during a transparent simulation run.” Running mdg transform twice over the same accumulated cache + seed is asserted byte-identical by test.

8状況パターン・ブラインド判定・認証（S7–S9）Situation patterns, blind judge & certification (S7–S9)

S7 — 状況パターンと比較ペア（凍結のあとだけ）S7 — situation patterns & contrast pairs (post-freeze only)

build_base_worlds（mdg/worlds.py）は、15以上の基本パターン（昼の通勤、夜の高速道路で眠気が高い/低い、渋滞、山道、単調な道、子ども同乗、推しモードのオン/オフ、休憩後の停車、最近聴いた曲あり など）を、共通のテンプレートの一部だけ書き換えて作ります。12組の比較ペアは「1つの項目だけが違う、2つの状況パターン」です： build_base_worlds (mdg/worlds.py) generates ≥15 deterministic base patterns (daytime commute, night highway with high/low drowsiness, congestion, mountain road, monotony, child present, oshi mode, stopped-post-rest, recent play, …) by overriding template fields. The 12 contrast pairs are two situation patterns differing in exactly one field:

pair-01-drowsiness: pattern A { driver.drowsiness_level: 20 } vs pattern B { driver.drowsiness_level: 90 } — 期待どおりなら、落ち着いた曲と元気な曲の順位が入れ替わるexpected: calm↔active song ranking reverses

AI が書けるのは、再生履歴や推しのプロフィール（direct_item_history／upro／usage_by_genre／scene_genre_usage）だけです。ドライバーや環境の項目には触れられません。状況パターン全体を機械的に走査し、凍結カタログに存在しない曲・アーティストへの参照が1つでもあれば、world_reference_failed で止まります。 The LLM may compose only history / oshi profiles (direct_item_history / upro / usage_by_genre / scene_genre_usage) — driver/environment fields are untouchable. Every situation pattern is regex-scanned; any synthetic-track-* / synthetic-artist-* reference absent from the frozen catalog halts with world_reference_failed.

S8 — ブラインド判定（答えを見ずに採点）S8 — the blind judge

AI は各（状況パターン, 曲）の組み合わせに positive／negative／neutral のラベルをつけます。このとき「P6 のスコアをまだ見ていない」ことが、仕組みとして保証されます：AI の出力に algorithm_score や agreement が先に入っていたら、BlindOrderingError で止まるのです。この検査を通ってからはじめて、本物の P6 evaluate() のスコアと突き合わせ、AI の直感と一致したかどうかを記録します： The LLM labels each (situation pattern, song) as positive / negative / neutral — and being blind to the P6 score is structurally enforced: if the LLM output already contains algorithm_score or agreement, it raises BlindOrderingError. Only after that check is the real P6 evaluate() score revealed and agreement recorded:

neutral band = |score| < 0.10
label = neutral → agree ⇔ |score| < 0.10
label = positive/negative → agree ⇔ sign(score を帯で符号化banded) = sign(label)

この「一致したか」は答え合わせのための記録で、目指すべき点数ではありません。不一致は judge_disagreement という印がつくだけで、エラーにはなりません。 Agreement is a cross-check, never a target. A disagreement is recorded as the data status judge_disagreement — not treated as an error.

S9 — 認証（順位の逆転テスト）S9 — certification (reversal tests)

mdg certify は、P6 パッケージの evaluate をファイルパスから直接読み込んで動かします（ロジックのコピーや模倣は作りません）。各比較ペアの2つの状況パターンでランキングを実行し、指定した2曲の順位が入れ替わるかを確かめます： mdg certify loads the P6 package's evaluate directly by file path (never re-implemented) and runs the ranking over both situation patterns of each contrast pair, checking that the two designated songs' relative order flips:

reverses(pair) ⇔ ( rank_A(song_hi) < rank_A(song_lo) ) ≠ ( rank_B(song_hi) < rank_B(song_lo) )
落ちたら「集め直す」しかない（FR-027）The only fix is re-harvest (FR-027)

順位が入れ替わらなかったペアには re_harvest_signal が出ます。意味は「このマスに別の実在曲を集め直せ。数値の調整は絶対にするな」。テストに落ちたら、直すのはデータの側（もっと合う実在曲を探す）であって、アルゴリズムや数値を答えに寄せることではありません。これが、この仕組み全体の「ズルをさせない」大原則です。 A non-reversing pair emits a re_harvest_signal — “harvest a different real song for this cell; never tune numbers.” Certification failures are fixed by obtaining better real data, never by nudging the algorithm or the sample data toward a target. This is the load-bearing anti-cheating rule of the whole system.

9統合と現状Integration & current status

生成器はリポジトリ直下の独立したパッケージ（music_dataset_generator/、FR-030）で、アプリ本体は mdg を一切読み込みません。つながりは、proposal_contracts/ 以下のコミット済みファイルだけです： The generator is a separate repo-root package (music_dataset_generator/, FR-030); the runtime API never imports mdg. Integration happens purely through committed files under proposal_contracts/:

proposal_contracts/dataset/<dataset_id>/{ catalog.json, dataset_manifest.json, genre_affinity_v1.json }
proposal_contracts/test_cases/test_cases.json   proposal_contracts/build_reports/{ build_report.json, certification_report.json }
  • アプリ側の DatasetCatalogRegistry は読み取り専用で、全曲を同じ Song の型でもう一度検査します。1曲でも不正があれば、そのデータセットは丸ごと隔離されます。「一部だけ公開」は絶対にしません。DatasetCatalogRegistry (app side) is a read-only scanner that re-validates every song against the same frozen Song model. If any song is invalid the whole dataset is quarantined — never partially available.
  • genre_affinity_v1 は、使うかどうか選べる別ファイルの拡張です。本物のジャンル情報を、決めておいた12語（j-pop, j-rock, city pop, anime, vocaloid, enka など）に対応づけます。この拡張を作っても作らなくても、カタログ本体は1バイトも変わりません（SC-005）。genre_affinity_v1 is an opt-in separate-file extension mapping real Soundcharts genres into a frozen 12-term vocabulary (j-pop, j-rock, city pop, anime, vocaloid, enka, …). The catalog itself is byte-identical with or without it (SC-005).
  • 凍結前の作業データ（生のキャッシュ、来歴、台帳、AI との受け渡しファイル）は gitignore 済みの generation_workspace/ に置かれ、コミットされません。Soundcharts の認証情報は環境変数から読むだけで、どこにも書き込みません。Pre-freeze generation state (raw cache, lineage, ledger, LLM I/O) lives in the gitignored generation_workspace/ and is never committed. Soundcharts credentials are read from the environment only and never written anywhere.
