## ⚠ V1 SCOPE — HARD BOUNDARY

> **V1 covers exactly two trigger signals, and only the one proposal that immediately follows each.**
> Read this before designing a case, a checkpoint, or a panel. Everything else in this
> document is scoped by it.

**In scope**

| | |
|---|---|
| Trigger categories | `rest_required` and `monotony_prevention` — **no other category** |
| The proposal reviewed | the service + content decision produced **at the moment the trigger fires** |
| `monotony_prevention` → | `trigger_purpose: inattentive_driving_prevention_recovery` · `lifecycle_stage: active_driving_content` |
| `rest_required` → | `trigger_purpose: rest_recommended` · `lifecycle_stage: before_rest_until_stop` (still driving, heading toward the spot) |

**Out of scope**

- **The rest spot itself** — `during_rest_stopped`. Not reviewed.
- **Anything after the rest** — `after_rest_before_restart`, nap recovery, re-energizing content, restart. Not reviewed.
- Every other trigger purpose — `route_music`, `child_passenger_experience`.
- Stopped-only services (`full_karaoke`, `stretch_video`, `relaxation_multisensory`, `oshi_reexperience`, `call_response_stopped`). They can only become eligible at an out-of-scope stage, so within V1 they appear **only as exclusions** in the centre panel — never as a reviewable rank-1.

**The simulator still runs the whole journey.** The rest lifecycle continues to play in the
centre panel — route, playback, rest acceptance, recovery, after-nap proposals all keep
working exactly as they do today. V1 narrows *what is reviewed*, not what is simulated.
Do not remove working lifecycle behaviour to satisfy this boundary.

**Consequences to settle before building the catalog**

- A full-rest-lifecycle case contributes only its **first** checkpoint to V1; its stopped and after-nap checkpoints are simulated but not reviewable.
- A contrast pair set at the after-nap stage (e.g. an oshi contrast, whose differentiating service is stopped-only) must be **re-cast at an in-scope stage or deferred to V2**. Oshi personalization is only observable in V1 through content, not through service selection.
- The checkpoint rail must expose in-scope decision points only; out-of-scope stages remain visible on the timeline as journey events.

## 1. What the customer actually asked for

The loop the customer wants is:

```text
use case  (driver profile + route + scenario — the existing presets)
  → run the three default algorithms          = the BASELINE
  → a human judges whether the outcome is appropriate
  → trace and explain WHY that outcome happened     ← the part they care most about
  → judge whether each parameter / hyperparameter is rational
  → modify parameters to make the algorithm better
```

There is **no pre-authored expectation** anywhere in that loop, and the customer does not want to write one. The reference point is what the current algorithms do; the judgement is human; the deliverable is a defensible argument about each parameter.

## 2. The fact that forced this redesign

The `expectation` blocks in the 35 committed `proposal_contracts/presets/*.json` were **generated by an LLM from the default three algorithms**. They record baseline behaviour. `top_fit_min` values (0.191, 0.216 …) are observed-then-recorded, and `proposal_preset_analysis.md` reports 35/35 passing only after `content_category_weights` was retuned to 0.45/0.35/0.20.

They are therefore a *record of the baseline*, not an independent specification, and cannot serve as the fixed reference an evaluator needs.

## 3. Relationship to the 2026-07-24 design

The 2026-07-24 design treats the expectation as an **input**: checkpoints are authored, then graded `MATCH` / `PARTIAL_MATCH` / `MISMATCH`. That design is sound, but it presumes ratified expectations exist.

The customer needs the expectation as an **output** — it is what human review produces.

The two are **sequential phases, not alternatives**:

- **Phase 1 (this design)** — baseline + trace + human judgement. Every time a reviewer records *"this is appropriate, because …"*, a ratified expectation with a justification comes into existence.
- **Phase 2 (2026-07-24)** — once enough ratified expectations accumulate, freeze them as checkpoints and the evaluator becomes meaningful: it catches regressions and the "right output for the wrong reason" case.

Nothing in the 2026-07-24 contract, registry, resolver or evidence-adapter design is invalidated. Only the *review surface* is replaced.

## 4. Goals

1. Run a committed use case through the three real algorithms and present the outcome plainly as the **baseline**, never as an expectation.
2. Explain **why** that outcome happened, in language a domain expert can argue with, without hiding the numbers from an engineer.
3. Let a human judge each parameter's influence as rational / too strong / too weak / not relevant / not sure.
4. Capture that judgement, plus a verdict on the decision and a free comment, and export it as evidence.
5. Keep persona, journey and algorithm setup fully editable, with the **detailed** setup being the existing Combined screen editors, unchanged.

## 5. Non-goals

- No pass/fail verdict, no status aggregation, no first-divergence banner. Nothing is graded.
- No authored expectations, checkpoints or contracts in this phase.
- No automatic parameter optimisation or recommended numeric values.
- No re-running of any algorithm to produce an explanation. Everything is arithmetic over recorded evidence.
- No claim that simulated sensitivity proves real-world causality.
- **No review of the rest-spot or after-rest stages, and no trigger category beyond the two named in the scope boundary above.** They are simulated, not reviewed.

## 6. Screen layout

Three columns, **20 % / 45 % / 35 %**.

### 6.1 Left — the use case and its setup

- **Experience test case picker** — one `<select>`, `optgroup`-grouped into Journeys and Contrast pairs. A chip shows the number of parameters flagged for that case.
- **Case card** — a two-sentence *brief* (what the case is and why it is worth running), a **What to watch** chip row naming the situation/preference dimensions to focus on, and a one-line persona + duration. A **Case details** popup carries the persona narrative, goals, preferences, constraints, assumptions, and the conditions the case fixes.
  *Deliberately absent:* expected outcome, expected causal path, journey narrative, event list, automatic path, resolved artifact references. The customer does not read them.
- **Contrast — simulated sensitivity** — for a paired case: the changed input path, the A/B switch, and the delta table (changed input → causal contribution → trigger-time → service-rank → content-result), each row marked material or unchanged.
- **Setup panel** — the built Combined setup panel: route preset + BYO-key custom route, rest-spot filters, tick duration, run seed, then Situation & scenario / Driver profile / Trigger / Service / Content, each an inline dropdown with an **Edit** button (§9).

Each control carries an informational badge — 🚗 *situation* (changing it reviews the same algorithm somewhere else) or ⚙ *algorithm* (changing it reviews the same situation under a different configuration — the tuning loop). These are labels, **not locks**: there is no Ad hoc mode and nothing greys out. When the setup differs from the case as defined, a note says so and offers Reset.

### 6.2 Centre — what the product did

Quickview timeline (road bands, jam sub-bar, both score curves, threshold, fire markers, rest markers) → playback controls → checkpoint rail → schematic route map → a **decision band** naming the decision point → **① Service proposal** and **② Content proposal side by side**, content wider (42/58) because it carries more.

Every song row in the content card is selectable as the review target; a separate chevron expands its contribution chain in place.

The playback loop must redraw only the timeline/rail/map/clock — never the proposal cards, or expanded chains collapse mid-run.

Per the scope boundary, the **checkpoint rail lists only in-scope decision points** — the
first `rest_required` or `monotony_prevention` fire and its immediate proposal. Rest
acceptance, the stopped stage and the after-nap proposal still animate on the timeline and
map as journey events, and their proposal output is still visible in the centre; they are
simply not selectable as a review target.

### 6.3 Right — whether the reasoning holds up

Stage tabs (Trigger / Service / Content), then:

1. **What decided it** (§7)
2. **Parameter rationale** (§8)
3. **Your assessment** (§10)

## 7. What decided it

### 7.1 Side-by-side comparison

Two dropdowns select what is compared; default is 1st vs 2nd. Every parameter is drawn as a **mirrored bar pair on one shared scale** — its contribution to the left option and to the right option — with a `◀ / ▶` lean marker showing which side it pulls toward and by how much.

This replaces a single aggregate bar, which reviewers could not read.

**Scale.** One bound across both columns, rounded up to the first readable value strictly above the largest magnitude: 0.299 → **±0.3**, 0.11 → **±0.125**. The bound is displayed; bars are never shown without it.

**Why the margin, not the total.** A feature can be the largest contributor to the winner and contribute nothing to the *gap*. In C-05 the old view reported drowsiness as the top contributor at 32.4 %; the margin view shows the decision was made by fatigue (60 % of the gap) while monotony pushed hard the other way and lost. Same evidence, opposite conclusion about which parameter to look at.

### 7.2 Presentation layer

- **Verdict sentence** first — *"Music playlist was chosen mainly because of how tired the driver is, despite how monotonous the road is."*
- **Domain grouping** — contributions bucketed into **Driver state · Road & environment · Preferences & history · Content properties**, shown for both options. This gives a specification-level judgement no per-parameter view offers: *"this decision leaned 49 % on driver state and gave preferences 1.5 % — for a music proposal, that is wrong."* The bucket assignment is a product decision, not a technical one; `driving_time` and `motion_state` in particular are arguable and belong to whoever owns the spec.
- **Raw-value anchoring** — every row leads with the value the reviewer already understands (`88 · very high`) before any derived number. This is the bridge the trace was missing: the evidence starts at *normalized*, the reviewer lives at *raw*.
- **Plain phrasing** — `monotony_level` reads as *"how monotonous the road is"*. The identifier stays visible in faint grey; it is never the label.

### 7.3 Trigger

The two sides are **the two trigger categories** (`rest_required` vs `monotony_prevention`) — which
in V1 is the complete category set, so the comparison is exhaustive rather than a top-2 slice. Both are scored from the same smoothed feature vector with different weight profiles, so the runner-up's per-feature contributions are derivable from recorded evidence. The threshold does not disappear: `firing threshold 0.70 · clearance +0.010` sits under the pickers.

**Proposed second mode (not built):** *compare with an earlier moment* — the same parameters at this tick versus 20 minutes ago, answering *"why did it fire now and not earlier?"* This is the more natural trigger question but needs per-tick factor snapshots the trace does not keep (§11).

### 7.4 Content

In V1 the plan under review is always the one produced at the trigger, for a
driving-capable service. Any item in that plan can be the review target. Position 1 is compared with the runner-up (*"why did this win?"*); any other position is compared with **the item above it** (*"why is it here and not higher?"*), so the margin reads negative and the decomposition shows what it lacks.

## 8. Parameter rationale

A table, ordered by realized influence, with a per-row assessment.

| column | meaning |
|---|---|
| **input** | plain phrase; identifier in the tooltip |
| **situation** | the raw value at this decision point, plus a strength word |
| **declared** | `normalize(base_weight × purpose_multiplier)` — the *intended* share of influence |
| **realized** | `\|contribution\| / Σ\|contribution\|` — the share it actually took |
| **↑ ↓ ≈** | `realized / declared`. Algebraically this reduces to the feature's evidence magnitude relative to the weighted average, so ↑ means *this feature's evidence is unusually extreme here* |
| **your view** | dropdown: — not judged — / Makes sense / Too strong / Too weak / Not relevant here / **Not sure** |

Two further computations feed the panel but are **not shown as columns** — reviewers could not interpret them numerically:

- **Necessity** — mask the feature, redistribute its weight, recompute: does the same option still win?
- **Flip distance** — the `purpose_multiplier` factor at which the outcome changes, found by bisection over the recorded chain.

They surface instead as sentences under **What a different setting would do**:

> Remove *how tired the driver is* and this decision becomes Call & response (driving).
> If *how monotonous the road is* mattered about 35 % more, Call & response (driving) would have been chosen instead.

And **Played no part in this decision** lists inputs with a realized share below 2 %, because their absence is often the most reviewable fact — *"the driver's registered favourite artist played no part"* may well be a bug.

Both sections are **suppressed for the trigger stage**; they only make sense against a named alternative option.

Necessity and flip distance are single-parameter, everything else held fixed, and local to one decision. No combinatorial sensitivity search.

## 9. Setup editors — two tiers

Each of the five editors opens in a **basic** view and carries a **▸ Detailed setup — every parameter** button that switches to the full view and back.

### 9.1 Basic tier

Only what a reviewer routinely turns:

| editor | basic content |
|---|---|
| Trigger | `threshold_suggest` (propose a rest), `monotony_suggest_threshold` (propose a monotony intervention) |
| Service | the three top-level `hierarchy_weights` shares (Situation / Preference / History) + `top_k` |
| Content | the three `content_category_weights` + `plan_item_count` + the α/β `context_response_matrix` |
| Situation | only what **this test case fixes** (from its own overrides) + driver state at departure |
| Driver profile | only what **this test case fixes** + the persona's defining preferences and assumptions |

Where a case pins nothing in that area, say so rather than showing an empty box.

### 9.2 Detailed tier — **REUSE, DO NOT REIMPLEMENT**

> **This is the most important constraint in this document.**
>
> The detailed view of every editor **must mount the existing Combined-screen component verbatim.** It must not be re-styled, re-laid-out, re-grouped, or re-created from the package manifests. Feature 020 already did this extract-and-share work and `MergedSetupPanel` already mounts these components; the review screen inherits that, unchanged.

Required mounts, exactly as `MergedSetupPanel` does today:

| Edit button | Component to mount | Notes |
|---|---|---|
| Situation | `FixedConditionsSection` + `SituationFieldRows` (route_tags, destination_tags, multiple_passengers) + `RouteConditionsPainter` + `SpeedProfileSection` + `SimulatedSignalsSection` | the A / painted / B / C layout |
| Driver profile | `PreferenceHistorySection` | drives `PROFILE_GROUPS` from `worldFields.tsx` |
| Trigger package | `AlgorithmFormulationPanel` | formula sections with inline coefficients, threshold ladders, fire-control steps |
| Service package | `ServiceSetupSection` | Setting → preprocessing → response coefficients → weights → advanced |
| Content package | `ContentSetupSection` | same five sections |

All of these are mounted inside `Modal` with **`size="wide"`** (`.modal-card--wide`, `width: 920px`), and they in turn use the shared table primitives — `HyperparamMatrix`, `ResponseMatrixTable`, `HierarchyWeightsTable`, `ScalarTable`, `ContentHierarchyTable` and `matrixStyles.ts`.

Rationale: these editors encode a large amount of design that is not recoverable from the manifests — `HierarchyWeightsTable` is a six-column rowspan grid, `ResponseMatrixTable` puts services across the top and features down the side, `ScalarTable` and the borderless 52 px matrix inputs are visually distinct, and `SignalRow`/`SignalGroup` have their own layout. Rebuilding them from the manifest **was attempted in the prototype and produced a materially different UI.** The prototype's detailed views are an approximation and are explicitly **not** the specification — the components are.

The prototype's *basic* tier and the two-tier switch are new and should be built; the *detailed* tier is an existing component behind a button.

### 9.3 Editing semantics

Any setup edit is legitimate and applies immediately (the editors are store-driven). The panel records only which loop the reviewer is in — situation or algorithm — and notes when the setup differs from the case as defined, with a Reset. No mode, no lock, no greying.

## 10. Feedback capture

Two levels, both keyed to `(case · decision point · stage · target)`:

- **Per-input judgement** — the dropdown in §8.
- **Per-decision assessment** — *Is this decision appropriate for this situation?* → Appropriate / Not sure / Not appropriate, plus a free comment for what they expected instead and why.

The assessment card opens with a **summary of the per-input judgements made at that decision**, and an *n / m inputs judged · k still open* count so the reviewer can see how much of the decision they have actually examined.

**Export** produces JSON carrying both levels plus the package versions in play:

```json
{ "decision_assessments": [ { "case_id", "checkpoint", "stage", "target", "assessment", "comment" } ],
  "input_judgments":      [ { "case_id", "checkpoint", "stage", "target", "feature_id", "judgment" } ],
  "packages": { "trigger", "service", "content" } }
```

In the real application this is the M5 append-only feedback store, not a download.

**"Not sure" is not a flag.** The flag counts on the picker and the checkpoint rail tally only the three criticisms; *Not sure* is a request for explanation, not a complaint, and must not inflate a number that means "these need attention".

**Cross-case aggregation (designed, not built).** One case cannot show a weight is wrong; a pattern across the catalog can — *"`fatigue_level` purpose_multiplier flagged too strong in 7 of 12 monotony use cases"*. That, plus a change preview showing which cases flip when a parameter moves, is what closes the tuning loop. Deferred until the single-case review is trusted.

## 11. Evidence requirements and known gaps

Everything in §7–§8 is computed from evidence already recorded. Four gaps limit what can be answered:

1. **Content candidate pool is not recorded.** A completed run keeps the 5 ordered items and an `excluded_items` array that is empty in practice; `input_snapshot` holds no candidate pool. So *"why is this song in the plan?"* can only be answered relative to items **in** the plan, and *"why isn't song X here?"* cannot be answered at all. **Fix:** record the scored tail — top ~20 non-selected items with fit and contributions — plus the cut margin. Additive.
2. **Bridge stage records no per-feature contribution.** `merged_adapter` carries facts across but not influence, so no rationale review is possible at that stage.
3. **Trigger runner-up category has no recorded per-feature evidence.** It is derivable (same smoothed vector, different weight profile) but is currently reconstructed rather than read. Recording both categories' contributions would remove the reconstruction.
4. **No per-tick factor snapshots**, which is what blocks the "compare with an earlier moment" trigger mode in §7.3.

Where evidence is missing the panel must say so. It must never infer a contribution.

## 13. Implementation boundaries

Suitable for one plan in four slices, each leaving Trigger, Proposal and Combined backward-compatible:

1. **Evidence adapters + review math** — margin decomposition, intent-vs-effect, necessity, flip distance, domain grouping, plain phrasing. Pure functions over recorded evidence; no algorithm invoked.
2. **Right panel** — stage tabs, side-by-side comparison, parameter rationale, consequences, played-no-part.
3. **Feedback capture and persistence** — per-input judgement, per-decision assessment, summary, M5-backed persistence and export.
4. **Setup two-tier switch** — the basic views, plus the button that reveals the existing editors (§9.2). Plus the layout changes: 20/45/35, proposal output moved to centre side by side, contrast moved to left.

Evidence extensions in §11 are separate, additive, and can land independently.

All four slices are bounded by the V1 scope: the review surface is wired to the two trigger
categories and their immediate proposal only. Extending it to the rest-spot and after-rest
stages is a V2 decision, and the evidence for those stages is already recorded — the work is
in the review surface and the catalog, not in the engine.

## 14. Acceptance criteria

1. Selecting a use case runs it through the three real algorithms and labels the result as the baseline, with package versions shown.
2. For any decision, the reviewer can see which inputs decided it *relative to a named alternative they can choose*, on one shared scale.
3. Every number is anchored to the raw situation value it came from.
4. Necessity and flip distance are stated as consequences naming the alternative, not as bare numbers.
5. Inputs that played no part are named.
6. A reviewer can record a judgement on every input and on the decision, and export both with the package versions.
7. **Every detailed setup popup is the existing Combined-screen editor component, mounted unchanged in a wide modal.**
8. No explanation component invokes an algorithm or alters a score, ranking or gate.
9. Where required evidence is absent, the panel says so and does not infer it.
10. **Only `rest_required` and `monotony_prevention`, and only the proposal made at the moment each fires, are reviewable.** The rest-spot and after-rest stages still simulate and display, but expose no review target.
