## 1. 目的とスコープ

AICA 仮説シミュレーターの **統合（Combined）画面** の操作マニュアルを、既存の 2 冊
（`aica-simulator-manual-ja.html` / `aica-simulator-proposal-manual-ja.html`）と
**同じ構造・スタイル・デザイン**で作成する。

統合画面は、1 つのテストケースを選ぶと、**発火判定（トリガー）→ サービス提案 →
コンテンツ提案** の一連の流れを 1 画面で通しでレビューできる画面。本マニュアルは
C-02 を実際に走らせながら、各パネルの読み方と操作を解説する。

### 非スコープ

- 統合画面以外（既存の Setup / Review / Proposal 画面）の再解説はしない（既存マニュアルへ委譲）。
- アルゴリズムの数式の全文再掲はしない（Appendix A は「変更点」だけを平易に説明）。

## 2. デザイン（既存マニュアルに完全準拠）

参照元 2 冊と同一の CSS トークンとコンポーネントを踏襲する：

- **レイアウト**: 左のスティッキー・サイドバー・ナビ + 本文カラム（`.layout` / `nav.sidebar` / `.wrap`）。
- **表紙**: 濃紺グラデーションの `header.cover`（kicker / h1 / badges）。統合画面向けに色味を1系統（teal/indigo）に。
- **見出し**: 番号付き `<h2><span class="num">`、`<h3>` / `<h4>`。
- **コールアウト**: `.callout.use`（💡 実践のヒント）と `.callout.note`（⚠ 注意）。
- **手順**: `.steps` の番号付き縦リスト。
- **表**: `.scroll > table`（横スクロール対応）。
- **図**: `figure > img` + `figcaption`（`.tag` 付き）。
- **クリックで拡大（重要要件）**: 参照元と同一の **lightbox**（`#lightbox` + 末尾 `<script>`）。
  全図がクリックでズーム、背景/Esc で閉じる。
- スクリーンショットは **base64 インライン**埋め込みで、ファイル単体で完結・全図ズーム可能にする。

1. **画面の全体像とワークフロー** — 統合画面が何をする画面か。1 ケースを選ぶと発火→サービス→
   コンテンツを通しでレビューできる。3 パネル構成（左=ケース選択+セットアップ / 中央=再生・地図・提案 /
   右=レビュー3タブ）。ナビの **統合** タブと **ライブ / 実行履歴**。
2. **テストケースの選び方** — `ExperienceCasePicker` とケースカード。C-02 の
   注目点 / ドライバー / 前提を実物で読む。
3. **左パネル — ケースカードとセットアップ** — C-02 が固定する条件（夜間 ON・初期眠気 60・
   Tokyo→Osaka・NRI）。A/B/C の各群。渋滞・山道区間の描画（Appendix A への布石）。
4. **中央パネル — 再生・地図・提案の流れ** — 再生コントロール（再生/一時停止/ステップ/リセット・速度）、

5. **右パネル — レビュー（発火判定・サービス・コンテンツ）** — 3 タブの読み方。寄与行・支持/反対。
6. **【実践】C-02 を通しでレビューする** — 押す順に沿った通し手順（発火→休憩受諾→サービス→

## 5. Appendix A — アルゴリズムの変更点（平易・コード検証済み）

低テク読者向けに「何がどう変わったか」を平易に。**アルゴリズム別**に正確に記述する。

### A-1 トリガー（発火判定）アルゴリズム

- **単調トリガーが安全トリガーより先に出る**：
  NRI（C-02 で使用）は 1 本のスコアを 2 つのしきい値で帯分けする。**単調性のしきい値の方が低い**ため、
  走行中スコアはまず単調性帯に入り（＝単調トリガーが先に出うる）、さらに上がって初めて休憩（安全）帯に入る。
  同じティックで両方に該当した場合は **休憩（安全）を優先**して 1 件だけ出す。
  （出典: `nri_fatigue_score_v1/algorithm.py` の帯分けと priority）
- **30 分以内の重複提案を出さない**：
  **透明ハイブリッド・トリガー**は、直近 30 分の提案数上限（`max_proposals_per_30min`）と
  カテゴリ別クールダウンを持ち、同じ提案が短時間に重複しないよう制御する。
  （出典: `aica_transparent_hybrid_trigger_v1/algorithm.py` 30-min count limit / cooldown）
  ※ C-02 の NRI 自体はクールダウン/30分上限を持たない点は正直に注記する。
- **渋滞・山道をシナリオ設定で再現**：
  セットアップで **渋滞区間・山道区間を km レンジで指定**してルート上に描画できる
  （`mountain_range_km` / `jam_range_km` / `jam_speed_kph`）。これによりトリガーの効き方を
  渋滞・山道ありで検証できる。（出典: `MergedSetupPanel` + `merged_painter.inject_mountain_segment`）

### A-2 コンテンツ提案アルゴリズム

- **推し（oshi）アーティストの複数登録＋お気に入り度**：
  以前は推し 1 名の完全一致だったが、いまは **複数の推しアーティストを登録**でき、各アーティストに
  **お気に入り度（熱狂度, 0〜1）** を設定できる。曲のスコアは、その曲に関わる推しのうち
  **最も熱狂度が高いもの**で決まり（合算ではなく最大）、コンテンツ提案スコアに反映される。
  （出典: `aica_transparent_content_selector_v1/algorithm.py` の `oshi` リーフ、feature 025 S2）

## 6. Appendix B — リカバリーモードのやさしい解説

`recovery_mode_explained.md` の内容を低テク向けに噛み砕く。技術用語を避け、
「受諾したあと何が起きるか」を絵と一緒に説明する。quickview の曲線
（ハイブリッド／NRI）を可視化に用いる。

### B-1 単調トリガーのリカバリー（かんたん）
- ドライバーが提案を **受諾すると、単調スコアを設定した点数ぶん即座に下げる**。
  運転は止めない（コンテンツで気分転換するイメージ）。下がったスコアはまた少しずつ溜まる。

### B-2 安全トリガーのリカバリー（休憩を伴う）
- 受諾した**その時点で、休憩地点に着くまでの間、眠気・疲労・渋滞の蓄積などを「フリーズ（凍結）」**する。
  → 休憩を決めたのに到着前に状態が急上昇するのを防ぐ。
- **休憩地点で休んだあと、眠気・疲労を設定した点数ぶん即座に下げる**（リカバリー）。
- ハイブリッドと NRI で内部の下げ方は違うが、**見た目の結果（休憩まで高止まり→休憩後に下がる）は同じ**
  という点を平易に。

### B-3 これは「プロトタイプ版の簡易リカバリー」— 将来の改良案
現状は「一括で固定点数を引く」簡易版。将来はより現実的にできる、として低テク向けに提案：
1. **時間で少しずつ回復**：仮眠 10 分より 30 分の方が眠気が大きく下がる、というように
   休んだ時間に比例して回復量が増える。
2. **活動の種類で回復が変わる**：ストレッチ・仮眠・カラオケなど、活動ごとに眠気/疲労のどちらに
   よく効くかを変える。
3. **回復にも「立ち上がり」を持たせる**：仮眠直後は少しぼんやり（睡眠慣性）してから効く、など
   一瞬で全快しない曲線にする。
4. **運転再開後のリバウンド**：休憩効果は永久ではなく、走り続けると再びゆっくり戻る（既に一部あり／
   もっと自然な曲線に）。

## 7. スクリーンショット取得方針

- **ドライバ**: Playwright + Chromium（インストール済み）で **Docker フロントエンド `:5180`** を操作。
  （社内プロキシは `--noproxy` で回避、疎通確認済み。htmlapp 単一ファイルも予備手段として利用可。）
- **地図**: **実 Google マップ**。Maps キーは **実行時に UI へ入力**するのみで、HTML/ログ/エクスポートには
  一切残さない（`app/frontend/.env.local` の値を実行時入力に使用）。
- **手順**: 統合画面 → C-02 選択 → 各パネルを撮影 → 再生して発火（休憩提案）→ 休憩受諾 →
  サービス／コンテンツ提案 → リカバリー可視化（quickview: ハイブリッド／NRI）。
- 取得用スクリプトは `others/debug/` 配下（成果物には含めない）。
- 図は base64 でインライン化し、全図 lightbox でズーム可能にする。
