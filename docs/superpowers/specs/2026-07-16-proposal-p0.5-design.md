# P0.5 — Content Contract & Song-Schema Freeze — Design

**Date:** 2026-07-16
**Milestone:** P0.5 (from `docs/master/aica_proposal_simulator_milestones.md` §2.5)
**Branch:** `proposal-p0.5-content-schema-freeze`
**Status:** Approved design (brainstorming complete); precedes SpecKit `speckit-specify`.

---

## 1. Goal & customer-visible outcome

Freeze the exact, versioned contracts the transparent **content-selector** package
validates against, so the content package (P6) can be authored and unit-tested in
complete isolation and the synthetic-dataset generator (P2) can consume the same
frozen shapes as its validation target. The outcome is a reviewable set of
**versioned Pydantic contract modules + exported JSON-Schema + a feature-disposition
registry + hand-authored, algorithm-blind fixtures**, together with the master-doc
reconciliations the freeze requires. This milestone pulls contract-definition work
forward from P1/P6.

There is **no** screen, runtime endpoint, ranking logic, dataset generator, journey
engine, frontend, or LLM/network path in P0.5.

## 2. Scope

### 2.1 In scope (freeze)
1. **Common selector input contract** (shared by both selector types) — Spec §5.3.
2. **Content-selector output contract** (`complete_plan`) — Spec §5.4 + content-algo §13/§14. **No aggregate plan score.**
3. **Song schema** — `spotify_track`, `spotify_audio_features`, `simulation_flags` (data-spec §4–6) + optional `genre_affinity_v1` extension shape (data-spec §21.1).
4. **Shared enums** — `trigger_purpose`, `lifecycle_stage`, service IDs, rest-spot type, content decision/error codes, disposition + provenance enums.
5. **Feature-disposition registry** for every Spec §9 / Appendix A.2 content row.
6. **Hand-authored, algorithm-blind fixtures** (smoke songs; calm/active, bright/dark, acoustic/electric pairs; world/feature snapshots; negative fixtures).
7. **JSON-Schema + registry export** committed as language-neutral frozen artifacts.
8. **Master-doc reconciliation** for the §17 items the freeze resolves.

### 2.2 Approach decision (recorded)
Freeze the **shared input contract + content output + song schema + shared enums**
now; the **service-selector output** contract is deferred to P1. This is the exact
P0.5 line the milestone draws and the minimum that lets P6 be built in isolation.
Freezing the service output now was rejected (YAGNI: no P0.5 acceptance criterion
drives it, and service scoring semantics — dominance, safety bands — are a P5
concern that could force a revision).

### 2.3 Out of scope (deferred, by milestone)
Content scoring logic (P6); dataset generator/validator/repair loop (P2); the
4-panel screen and neutral run/persistence types (P1); editable world (P3); journey
engine value semantics (P4); all frontend/i18n; any LLM or network path;
service-selector output contract (P1); dataset-level identity/coverage validation (P2).

## 3. Ownership model (why models live in the backend)

The established trigger convention (verified in the repo):
- Packages are `packages/<name>/algorithm.py` exposing `def evaluate(context: dict) -> dict` — **plain dicts in/out**, importing **nothing** from `aica_api`.
- The **backend** owns the Pydantic models; the adapter (`algorithms/python_module.py`) validates the context before calling `evaluate()` and validates/normalizes the returned dict. The model is the **adapter boundary**, not a package import.

Applying that convention to the proposal contracts:
- Proposal Pydantic contract models are **backend/API-owned**. Later milestones' orchestrator/adapter use them to build the selector input and validate/normalize the `complete_plan` a package returns.
- The future P6 content package is a `python_module` written as `evaluate(input: dict) -> dict`, working with dicts — it does **not** import these models.
- P0.5's "author and validate the content package against the frozen contract with no other milestone present" is met by: (a) the frozen Pydantic models as the authoring spec; (b) an **exported JSON-Schema** committed as a language-neutral frozen artifact the dict/JSON-based P6 package and P2 generator validate against without importing the backend; (c) hand-authored fixtures as concrete test data.

## 4. Module & artifact layout

### 4.1 Backend Pydantic contracts — `app/api/aica_api/models/proposal/` (isolated subpackage)
```
app/api/aica_api/models/proposal/
  __init__.py            # re-exports; CONTRACT_VERSION, SCHEMA_VERSION constants
  enums.py               # TriggerPurpose, LifecycleStage, ServiceId, RestSpotType,
                         #   ContentDecisionType/ContentErrorCode, FeatureDisposition,
                         #   FeatureOriginProvenance, ResponseCoefficientProvenance,
                         #   GenreLiteral, UsageLevel
  selector_input.py      # SelectorInput (common §5.3), FeatureProvenanceEntry,
                         #   CandidateRef, ExcludedCandidate
  content_output.py      # CompletePlan (§5.4/§14), OrderedItem, ItemFeatureContribution,
                         #   SongTraitValues, PlanMode, LightingConfiguration, ExcludedItem
  song_schema.py         # SpotifyTrack (+Album, ArtistRef, ExternalIds, ExternalUrls,
                         #   Image, Restrictions, LinkedFrom), SpotifyAudioFeatures,
                         #   SimulationFlags, Song (composed)
  genre_extension.py     # GenreAffinityV1, GENRE_VOCABULARY
  dispositions.py        # feature-disposition registry (single source of truth)
  export_schema.py       # `python -m aica_api.models.proposal.export_schema`
```
Isolation is deliberate (separation invariant): nothing in `models/proposal/`
imports trigger models, and the top-level `models/__init__.py` is **not** modified —
proposal contracts are imported via `aica_api.models.proposal`.

### 4.2 Repo-root frozen artifacts — `proposal_contracts/`
```
proposal_contracts/
  README.md
  schema/
    selector_input.schema.json
    content_output.schema.json
    song.schema.json
    genre_affinity_v1.schema.json
  dispositions/
    content_feature_dispositions.v1.json
  fixtures/
    songs/ { smoke/ , pairs/ , karaoke/ }
    worlds/
    negative/
```
- `export_schema.py` writes `schema/` and `dispositions/*.json` from the Pydantic models/registry. A test asserts the committed files match a fresh export (drift guard) — "generated via its generator, never hand-edited."
- Fixtures are hand-authored (algorithm-blind) and committed directly.
- `config.py` gains `AICA_PROPOSAL_CONTRACTS_DIR` (default repo-root `proposal_contracts/`), mirroring `AICA_PACKAGES_DIR`/`AICA_SCENARIOS_DIR`, so P6/P2 resolve artifacts by path without importing the backend.

## 5. Frozen contracts (field level)

### 5.1 Enums
- `TriggerPurpose`: `rest_recommended`, `inattentive_driving_prevention_recovery`, `route_music`, `child_passenger_experience`.
- `LifecycleStage`: `before_rest_until_stop`, `during_rest_stopped`, `after_rest_before_restart`, `active_driving_content`.
- `ServiceId`: all 14 catalog IDs (Spec §7.1–7.2) — `music_playlist`, `humming_karaoke`, `call_response_driving`, `quiz`, `ranking_creation`, `radio_style`, `conversation_audio`, `live_viewing`, `stretch_video`, `full_karaoke`, `call_response_stopped`, `oshi_reexperience`, `relaxation_multisensory`, `linked_video_recommendation`. (Full enum now even though only 3 have V1 content recipes — a package returning an unsupported one yields `unsupported_recipe`.)
- `RestSpotType`: `sa_pa`, `convenience_store`, `parking`, `oshi_spot`, `other`, `unknown`.
- `ContentDecisionType`/`ContentErrorCode`: `complete_plan`, `no_proposal`, `insufficient_eligible_items`, `unsupported_service`, `unsupported_recipe`, `invalid_request`, `invalid_catalog`, `invalid_configuration`, `full_karaoke_requires_stopped` (union of Spec §5.4 + content-algo §13).
- `FeatureDisposition`: `scored`, `context_only`, `available_but_not_used`.
- `FeatureOriginProvenance`: `cdc_su_baseline`, `normalized_cdc_su_concept`, `proposed_addition`.
- `ResponseCoefficientProvenance`: `cdc_su_explicit`, `service_definition`, `normalized_context_hypothesis` (+ any additional values the algo docs use) — kept **distinct** from feature-origin per boundary checklist A.3.
- `GenreLiteral`: the 12-term controlled vocabulary (data-spec §21.1). `UsageLevel`: `never`, `low`, `med`, `high`.

### 5.2 `SelectorInput` (common, §5.3)
`contract_version: str`, `opportunity_id: str`, `simulation_time: str|int`,
`trigger_purpose: TriggerPurpose`, `lifecycle_stage: LifecycleStage`,
`allowed_service_ids: list[ServiceId]` (non-empty),
`feature_snapshot: dict[str, Any]` (complete independent §8 or §9 snapshot; validated
structurally, not scored), `feature_provenance: dict[str, FeatureProvenanceEntry]`,
`enabled_feature_extensions: list[str]`, `selected_service_id: ServiceId | None`
(content only), `eligible_candidates: list[CandidateRef]`,
`excluded_candidates: list[ExcludedCandidate]` (each with a platform reason),
`parameters: dict`, `hyperparameters: dict`, `package_runtime_state: dict`,
`catalog_version: str`, `run_seed: str`.
- Model validator: purpose/stage compatibility — the three rest stages only with `rest_recommended`; `active_driving_content` only with purposes ②–④; `allowed_service_ids` non-empty.

### 5.3 `CompletePlan` (§5.4 + content-algo §14) — no aggregate plan score
`decision_type: ContentDecisionType`, `selected_service_id: ServiceId`,
`requested_item_count: int`, `returned_item_count: int`,
`ordered_items: list[OrderedItem]`, `mode: PlanMode`, `expected_duration_sec: int`,
`lighting_configuration: LightingConfiguration | None`, `approval_policy: str`,
`completion_rule: str`, `next_transition_policy: str`,
`excluded_items: list[ExcludedItem]`, `unused_available_features: list[str]`,
`missing_features: list[str]`, `algorithm_provenance: dict`.
- `OrderedItem`: `position`, `item_id`, `item_fit: float | None` (null for LLM), `trait_values: SongTraitValues` (`arousal`, `valence`, `humming_ease`, `full_karaoke_ease` + signed `A_s`, `V_s`), `feature_contributions: list[ItemFeatureContribution]` (empty for LLM), `rationale: list[str]`.
- `ItemFeatureContribution`: `feature_id`, `e_i`, `a_i`, `alpha`/`beta` **or** `exact_match` provenance, `r_i`, `base_weight`, `purpose_multiplier`, `mask`, `effective_weight`, `contribution`, `formula_version`.
- `PlanMode`: discriminated shape for playlist / humming (chorus-only, guide-vocal, no-driving-lyrics, `fixed_segment_sec`) / full-karaoke (stopped-only, simulated queue).
- **`approval_policy`/`completion_rule`/`next_transition_policy`** frozen as typed `str` with documented candidate values in the docstring; their value *semantics* are owned by the P4 journey engine. Freezing the fields (not the full value sets) is the correct P0.5 line.
- **No** `plan_score`/`aggregate_score` field exists anywhere in the output (a test asserts this).

### 5.4 Song schema (data-spec §4–6)
- `SpotifyTrack`: full V1 field inventory (§4.1: `album, artists, available_markets, disc_number, duration_ms, explicit, external_ids, external_urls, href, id, is_local, is_playable, linked_from, name, popularity, preview_url, restrictions, track_number, type, uri`), with conditional-presence rules for `is_playable`/`linked_from`/`restrictions`.
- `SpotifyAudioFeatures`: full §5.1 field set (18 fields).
- `SimulationFlags`: `humming_karaoke_available` / `full_karaoke_available`, each `Literal[0,1]`, default `1`.
- `Song`: composes the three; validators enforce per-record invariants (§4.3/§5.3): `type` literals; `[0,1]` ranges; `key ∈ {-1,0..11}`; `mode ∈ {0,1}`; `tempo>0`; finite `loudness`; `time_signature ∈ 3..7`; Track↔AudioFeatures `id`/`uri`/`duration_ms` agreement; `.invalid` host on every URL; `synthetic-` prefix on every synthetic ID. **Dataset-level** id-uniqueness/coverage is deferred to P2.

### 5.5 `GenreAffinityV1` (data-spec §21.1)
`artist_genres: dict[str, list[GenreLiteral]]`, optional `usage_by_genre: dict[GenreLiteral, UsageLevel]`, optional `scene_genre_usage: dict[str, dict[GenreLiteral, UsageLevel]]`. Validators enforce §17.7: vocabulary membership; no key added inside `spotify_track`/`spotify_audio_features`/`simulation_flags` (no-overwrite rule).

## 6. Feature-disposition registry & §17 reconciliations

### 6.1 Registry (single source of truth)
`dispositions.py` → `proposal_contracts/dispositions/content_feature_dispositions.v1.json`:
an ordered list, one entry per Spec §9 / Appendix A.2 **content** row, each with
`feature_id`, `category`, `subcategory`, `feature_name`, `disposition`,
`feature_origin_provenance`, `response_coefficient_provenance` (scored rows),
`genre_gated: bool`, `source_reference`, `rationale`. Dispositions taken directly
from content-algo §5.3/§6.1, reconciled with Appendix A.2's fuller row set:
- **15 `scored`** (Spotify-only V1): Situation 7, Preference 6, History 2.
- **6 `genre‡`** `scored` with `genre_gated: true` (route, destination, child, hobbies, content-tag/genre usage, scene/genre usage) — behave `context_only` when `genre_affinity_v1` is off (mask 0), `scored` when on.
- Oshi registered / oshi mode → `context_only` (gates that enable the Oshi ID score, not standalone scores).
- All remaining §9/A.2 rows (novelty/unused-content, cancelled plans, multiple-passengers, oshi type/tags, schedule, the 11 `Additional proposed` simulator rows) → `context_only` or `available_but_not_used` — **never dropped**.

### 6.2 §17 reconciliations resolved by this freeze
1. **Control-input naming** → normalize to `trigger_purpose` / `lifecycle_stage` everywhere; the content-algo doc's dotted usages are updated. *Rationale:* every other doc + the Pydantic enums use the flat names; one canonical form.
2. **Schedule-field ownership** → in the content contract all three schedule fields (`scheduled_event_type/timing/tags`) are `context_only` (present in snapshot, mask 0, never scored). *Rationale:* content-algo §5.3 marks all three not-scored; no Spotify song field supports an event relation; schedule→content affinity is deferred (content-algo §19). The service doc's "delegation to content" is satisfied by carrying them as visible context.
3. **Content `Additional proposed` dispositions** → every one of the ~14 A.2 `Additional proposed` rows gets an explicit disposition (`oshi_id` `scored`, relocated to Preference per §5.3; `oshi_type`/`oshi_tags` `context_only`; rest-route/session/confidence/granular-ops `context_only` unless §5.3 scores them). None silently dropped.
4. **Content-doc field renames** → under `genre_affinity_v1`, `content_tag_usage_level`→`usage_by_genre`, `scene_content_tag_usage_level`→`scene_genre_usage`; the registry uses the renamed fields; a cross-check keeps A.2 + data-spec §13 aligned.

Out of scope: **post-rest 4-vs-5 service count** (a P4/P5 service-side freeze item).

## 7. Fixtures (hand-authored, algorithm-blind)

- `songs/smoke/` — 5 valid `Song` records (data-spec smoke tier).
- `songs/pairs/` — three one-axis contrast pairs authored by construction, **not** scored: calm/active (arousal-axis fields), bright/dark (`valence`/`mode`), acoustic/electric (`acousticness`). They prove the schema *represents* the contrasts P6/P2 rely on.
- `songs/karaoke/` — one high-`instrumentalness` song with flags still `1` (eligibility is a gate; ease is a trait, not a gate).
- `negative/` — malformed records, each isolating one rejection rule (out-of-range `energy`, `mode:2`, `time_signature:8`, Track↔AudioFeatures id/duration mismatch, non-`.invalid` URL, missing `synthetic-` prefix, `simulation_flags` value `2`, out-of-vocabulary genre, `artist_genres` overwriting a track field).
- `worlds/` — 2–3 feature/world snapshots (data-spec §13): a night-highway world and its `genre_affinity_v1`-on variant. Algorithm-blind: they set fields, assert nothing about ranking.

## 8. Versioning
- `CONTRACT_VERSION = "1.0.0"` (selector input + content output), `SCHEMA_VERSION = "1.0.0"` (song schema), mirroring the docs' `contract_version`/`schema_version` split. Genre extension carries its own version tag.
- Disposition registry versioned in filename (`...v1.json`) and a `registry_version` field.
- These constants are what P1's setup snapshot will record; P0.5 defines and freezes them.

## 9. Test strategy & milestone-exit demonstration

New pytest files under `app/api/tests/proposal/` (run via the Anaconda 3.12 fallback `python -m pytest`; the canonical `docker compose exec api uv run pytest` is unavailable in this shell — Docker/uv network are unreachable):
- `test_selector_input_contract.py` — valid accepted; purpose/stage incompatibility rejected; missing/extra fields; content-only `selected_service_id`.
- `test_content_output_contract.py` — valid `complete_plan` accepted; **no aggregate-score field**; per-item contribution shape; decision/error-type coverage; LLM-shaped plan (`item_fit=null`, empty contributions) accepted.
- `test_song_schema.py` — every `songs/` fixture accepted; every `negative/` fixture rejected for the intended rule; cross-object identity.
- `test_genre_extension.py` — valid accepted; vocabulary + no-overwrite violations rejected; extension-off leaves the six rows `context_only`.
- `test_dispositions.py` — completeness, valid dispositions/provenance, genre-gated set, and the Appendix A.2 markdown cross-check.
- `test_schema_export.py` — committed `schema/*.json` + `dispositions/*.json` match a fresh export (drift guard).
- `test_docs_naming_consistency.py` — the dotted control-input form no longer appears as a field name in the master docs.

**Milestone-exit demonstration:** new `app/api/tests/proposal/` suite green + full existing backend suite green (regression gate); schema/registry artifacts exported and committed; each of the four milestone acceptance criteria mapped to a passing test. No server, frontend, or LLM.

## 11. Risks / notes
- **pydantic version delta:** local Anaconda has pydantic 2.8.2 vs container 2.13.4. All contract features used (Literal, model_validator, field constraints, `model_json_schema`) are stable across both. A CI/container run remains the authoritative gate when Docker is available.
- **JSON-Schema fidelity:** Pydantic's `model_json_schema()` is the export source; the drift-guard test pins the committed files to it so reviewers see exactly what P6/P2 consume.
- **`feature_snapshot` is `dict`, not a closed model, in P0.5:** the §8/§9 snapshot is validated structurally (keys/provenance), not field-by-field, because the full editable-world field models are P3's. The disposition registry is the authoritative content-field list until then.
