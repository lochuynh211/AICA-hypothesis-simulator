AICA proposal simulator / AICA提案シミュレーター

From “when to propose” to “what to propose next” 「いつ提案するか」から「次に何を提案するか」へ

A customer-review simulator for choosing an in-car service and its concrete content across pre-rest, rest, and post-rest situations. 休憩前・休憩中・休憩後を通して、車内サービスと具体的なコンテンツの選び方をお客様が確認・調整するためのシミュレーターです。

1. The proposal idea 1. 提案の基本的な考え方

The trigger purpose is supplied explicitly. The proposal algorithm receives one of four purposes, the current lifecycle stage, and the services allowed in that stage. It then uses situation and personal features to rank only those permitted candidates.

発火目的は明示的に入力されます。 提案アルゴリズムは4つの目的のいずれか、現在のライフサイクル段階、その段階で利用可能なサービスを受け取ります。そのうえで状況・個人特徴量を使い、許可された候補だけを順位付けします。

Four explicit trigger purposes明示される4つの発火目的

① Rest recommended休憩推奨 — rest_recommended ② Inattentive-driving prevention / recovery漫然運転予防・疲労回復 — inattentive_driving_prevention_recovery ③ Route-based musicルートに応じた音楽 — route_music ④ Child-passenger experience子供同乗時体験 — child_passenger_experience

Lifecycle constrains the servicesライフサイクルでサービスを制約

For purpose ①, the allowed choices change between driving to the rest spot, resting while stopped, and post-rest while stopped. Purposes ②–④ use the driving-content flow defined in Slide 65.

目的①では、「休憩所まで走行中」「停車して休憩中」「休憩後・再走行前」で選べるサービスが変わります。目的②～④はスライド65の走行中コンテンツフローを使用します。

Two decisions2段階の意思決定

First choose the service, such as playlist or humming karaoke. Then choose the actual playlist, songs, mode, and presentation.

まずプレイリストや鼻歌カラオケなどのサービスを選び、その後に実際の曲・モード・演出を選びます。

Three candidates3つの候補

Normally show three ranked service candidates and up to three concrete plans. The driver may reject or ask for alternatives.

通常はサービス候補を3件、具体案を最大3件提示します。拒否や別候補の要求も可能です。

Recalculate at transitions場面転換時に再計算

Preview the likely journey early, but commit only the next action. Recalculate after arrival, rest, motion change, or rejection.

将来の流れは早めに見せますが、確定するのは次の行動だけです。到着・休憩・走行状態変更・拒否の後に再計算します。

Safety first, but advisory. Impermissible behavior is removed. Safety then receives overwhelming ranking priority. The driver still makes the final choice; AICA proposes and does not force.

安全最優先、ただし提案型。 許容できない提供方法は候補から除外し、そのうえで安全性に圧倒的に高い優先度を与えます。最終的な選択はドライバーにあり、AICAは強制しません。

2. One end-to-end rest journey2. 休憩前から休憩後までの一例

This is a representative path from the use cases—not a fixed script. Each phase is confirmed again using the latest situation.

これはユースケースに基づく代表例であり、固定シナリオではありません。各フェーズで最新状況を使って再確認します。

Pre-rest: while driving休憩前：走行中

Propose a practical rest spot and an audio-first option for the drive there, such as chorus-only humming karaoke.

現実的な休憩場所と、そこまでの走行中に使える「サビのみ鼻歌カラオケ」など音声中心の案を提案します。

Rest: after arrival休憩中：到着後

The driver chooses the rest method and duration, for example a nap. The simulator applies an explicit post-rest state chosen by the reviewer.

仮眠などの休憩方法・時間をドライバーが選びます。休憩後の状態は、評価者が設定した明示的な値を反映します。

Post-rest: while stopped休憩後：停車中

Recalculate and offer stopped experiences such as full karaoke, live viewing, stretch, or an oshi-related experience.

再計算し、フルカラオケ、ライブ映像、ストレッチ、推し関連体験など停車中向けサービスを提案します。

Lighting is a presentation option, not a service by itself. It can accompany playlist, humming karaoke, call-and-response, live viewing, and full karaoke. It is not used for quiz, ranking, radio-style playback, stretch, or oshi reexperience.

ライティングは単独サービスではなく演出オプションです。プレイリスト、鼻歌カラオケ、合いの手、ライブビューイング、フルカラオケに利用できます。クイズ、ランキング、ラジオ風再生、ストレッチ、推し追体験では利用しません。

3. Four independent algorithm packages3. 4つの独立したアルゴリズムパッケージ

Service proposalサービス提案

  • Transparent scoring package透明なスコアリング方式
  • Constrained LLM package制約付きLLM方式

Returns up to three services from the set allowed by the explicit trigger purpose and lifecycle stage. It cannot add a service forbidden in that flow.

明示された発火目的とライフサイクル段階で許可されたサービス集合から最大3件を返します。そのフローで禁止されたサービスは追加できません。

Concrete-content proposal具体コンテンツ提案

  • Transparent scoring package透明なスコアリング方式
  • Constrained LLM package制約付きLLM方式

Returns actual plans: playlist items, humming mode, full karaoke song, duration, lighting, and ending behavior.

曲順、鼻歌モード、フルカラオケ曲、長さ、ライティング、終了方法などの具体案を返します。

Transparent scoring透明スコアリング

An expert-defined, customer-editable hypothesis. Every weight and contribution is visible. With no training data, the score is a fit hypothesis—not a probability or proof.

専門家が定義し、お客様が編集できる仮説です。重みと寄与をすべて表示します。学習データがないため、スコアは適合度の仮説であり、確率や正しさの証明ではありません。

Constrained LLM制約付きLLM

Uses the same facts and catalog, but makes an independent judgment. It must cite supplied fields and catalog IDs and may not invent songs, events, or user facts.

同じ事実とカタログを使いますが、独立して判断します。入力特徴量とカタログIDを根拠として示し、曲・イベント・ユーザー情報を創作してはいけません。

4. Exact features used4. 使用する特徴量の全体像

P0 is dominant safety/eligibility context; P1 is primary situation; P2 is contextual; P3 is personalization/history; P4 is a weak novelty or tie-breaker.

P0は安全・適格性に関わる最優先、P1は主要状況、P2は文脈、P3は個人化・履歴、P4は弱い新規性・同点調整です。

Source first: the CDC-SU features are the baseline. Features proposed by the simulator team are shown separately and are never presented as CDC-SU requirements.

CDC-SUを最優先：CDC-SU記載の特徴量を基準とし、シミュレーターチームの追加提案は別表に分け、CDC-SU要件として扱いません。

5. What the customer can do in the simulator5. お客様がシミュレーターでできること

Edit the complete world世界全体を編集

Edit trigger purpose, lifecycle stage, allowed-service matrix, every feature, schedule, oshi profile, catalog, event, parameter, and hyperparameter. Every feature is labeled CDC-SU baseline, normalized CDC-SU concept, or proposed addition.

発火目的、ライフサイクル段階、許可サービス表、すべての特徴量、予定、推しプロフィール、カタログ、イベント、パラメータ、ハイパーパラメータを編集できます。各特徴量には「CDC-SU基準」「CDC-SU概念の正規化」「追加提案」を表示します。

See cause and contrast原因と差分を確認

Clone a seed, change one field, and see eligibility, rank, reason, and journey changes. This makes the proposal idea easy to explain.

シードを複製し、1項目だけ変更して、適格性・順位・理由・体験の変化を確認できます。提案の考え方を説明しやすくします。

Review, not certify検証ではなく評価

The customer judges whether the result feels appropriate, understandable, safe, useful, or intrusive. The simulator records that review separately.

結果が適切、理解可能、安全に感じる、有用、煩わしいかをお客様が評価します。シミュレーターはその評価を別の証跡として保存します。

Interactive mode対話モード

Choose, reject, edit, request alternatives, and manually progress through events.

選択、拒否、編集、別候補要求、イベント進行を手動で行います。

Quick-check modeクイック確認モード

Automatically take the top valid candidate to inspect the resulting journey quickly. It uses the same ranking as interactive mode.

最上位の有効候補を自動選択して、結果の流れを素早く確認します。対話モードと同じランキングを使用します。

V1 is discrete event-driven. In the standalone screen, the customer selects the trigger purpose and starting lifecycle stage. Later, the trigger simulator will supply its selected purpose and tick/journey state through the same proposal contract.

V1は離散イベント駆動です。単独画面ではお客様が発火目的と開始ライフサイクル段階を選びます。将来はトリガーシミュレーターが、選択した目的とtick・ジャーニー状態を同じ提案契約へ渡します。

6. Delivery path6. 実装の進め方

1Separate screen and contracts別画面と共通契約
2Synthetic world and constraints合成世界と制約
3Transparent music journey透明方式の音楽体験
4Independent LLM packages独立LLM方式

The first customer-meaningful release is the transparent music vertical slice: editable data → service proposal → content proposal → pre-rest/rest/post-rest journey → evidence. LLM comparison follows on the same contracts. 最初にお客様へ価値を示せるリリースは、透明方式の音楽縦断体験です。編集可能データ → サービス提案 → 具体提案 → 休憩前/中/後 → 証跡までを実現し、その後、同じ契約上でLLM方式と比較します。
